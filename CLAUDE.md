## Commands

```bash
npm install
npm run dev          # http://127.0.0.1:3000 (loopback only)
npm run build        # production build; also type-checks
npm run start        # serve the build on 127.0.0.1:${PORT:-3090} (production, behind nginx)
npm run typecheck    # tsc --noEmit (delete .next first if it complains about moved pages)
npm run db:migrate   # apply db/schema.sql and add any newer columns (safe to re-run)
npm run db:portfolio # upsert the 10 showcase projects and their case-study copy (matched by site URL)
npm run media:upload # upload new/changed files in public/assets and public/og to DigitalOcean Spaces (+ resized WebP copies)
```

There is no test suite or linter. Verify by running the dev server and checking pages at desktop and narrow phone widths (main CSS breakpoints are 1180px, 1100px, 960px and 640px, plus 699px for three-card rows, 1101–1280px for small laptops, and 1800px/2200px where `--max` widens for large screens; on touch screens and up to 1024px small links get 44px targets). Check every width from 320px to 2560px, and avoid a lone card on a grid's last row for horizontal overflow, keyboard focus and reduced motion. The built-in browser pane only captures a corner of an emulated viewport; Playwright full-page screenshots (saved under the gitignored `.playwright-mcp/`) are more reliable. Scroll reveals keep below-the-fold content hidden until it is scrolled to, so before a capture run `document.querySelectorAll('.reveal,.tilt-in,.text-reveal').forEach(e=>e.classList.add('is-in','is-done'))` and inject `.rise,.page-enter,.dock{animation:none!important}`.

Configuration comes from `.env.local` (development) or `.env` (Ploi production); `.env.example` lists every variable. Both env files are gitignored and must never be committed. The local env points at the **real** DigitalOcean database, so anything you submit locally lands in production data: clean up test enquiries and portfolio items afterwards.

## Architecture

Next.js 16 App Router, TypeScript, React 19, MySQL via `mysql2`. No CSS framework; Lenis provides inertia scrolling and Lucide (`lucide-react`, pinned) provides every icon.

- **Pages:** public pages live in the `app/(site)` route group, whose layout adds `SmoothScroll`, `SiteHeader` and `SiteFooter`: home, `about`, `services` (overview) and `services/[slug]` (six service pages), `work` (all projects with service filters) and `work/[slug]` (one case-study page per project), `products` and `products/[slug]` (see Products below), `contact`, `terms` and `privacy` (both via `components/LegalPage.tsx`). `app/not-found.tsx` sits outside the group and renders the header and footer itself. Each page renders its own `<main id="main">`. Old `*.html` URLs redirect permanently in `next.config.ts`.
- **Service content** lives in `lib/services.ts`: names, slugs, copy, `topics` (the enquiry form's topic options and the server-side allowlist) and `serviceStyle` (icon and accent colour per service). A service with `hidden: true` keeps its content but is left out of `services` (so it isn’t shown, linked, offered as a form topic or listed in the sitemap), its page 404s, and `next.config.ts` redirects its URL to `/services`. Display numbers (01, 02…) follow the visible order. Currently hidden: cloud & infrastructure, AI & workflow automation, strategy & consulting. Service images are `public/assets/services/<slug>.png` and project covers are `public/assets/portfolio/<slug>.png` (both generated with Higgsfield). "How we work" steps are in `lib/process.ts`. The About page team ("Core team" and "Development team", three people each, rendered by `components/TeamGrid.tsx`) lives in `lib/team.ts`: names, roles and bios are placeholders to replace, and a member without `image` shows a placeholder portrait; real photos go in `public/assets/team/` (about 4:5) with their path set as `image`.
- **Shared chrome:** `components/SiteHeader.tsx` (client: a single floating "dock" bar with the logo, nav links beside it (current page marked by a small gradient square via `aria-current`), the email address and a gradient "Start a project" button; a Services panel that drops under the dock (Services is a button controlling `#services-menu`; it opens on hover, click or ArrowDown, closes on Escape, outside click, moving onto the dimmed page (`.nav-scrim`) or below 960px; its subtitles and "Popular" links are `featureCopy` and `offers` in the component, filtered to visible services); and below 960px a full-screen menu that stops Lenis, locks scrolling and closes on Escape) and `components/SiteFooter.tsx` (a strip of soft-square service tiles sliding in two rows, linking to the enquiry form, then link columns and the legal row). `components/SmoothScroll.tsx` starts Lenis (skipped under reduced motion), exposes it as `window.squaberryLenis`, and re-syncs it after every route change so Next.js's scroll-to-top sticks.
- **Building blocks:** `PageHero` (page opener for Projects, Services, each service page, About, Contact, Terms and Privacy: eyebrow and title on the left; lead, optional `aside` and `actions` on the right; only the 404 page keeps the centred `.page-hero`), `SectionIntro` (eyebrow label with a small gradient square, then a large heading; no rule line; `tone="light"` on lavender/cream panels), `ProcessSteps` (the four "How we work" cards used on home, Services and About: gradient icon tile in the step's accent, outlined step number), `ProjectCard` (framed cover image, name, headline, tags along the bottom; `featured` puts the image beside the text; links to the project page, or the live site if a project has no slug), `ProjectsBrowser` (client filter chips + bento grid for `/work`), `Icon` (maps short names such as `web` or `arrow-up-right` to Lucide icons; add new icons to its map, never hand-drawn SVG paths; the admin uses `AdminIcon`, also Lucide) and `EnquiryForm`.

The feature copy is a draft: the Fast Food system's comes from the Chips n Chops platform (`D:\Project\Github\ChipsnChops`: admin, API and mobile app); the others need confirming. Images are in `public/assets/products/` (Higgsfield); the gym and food galleries reuse the real site screenshots in `public/assets/work/`.
- `/products` (`app/(site)/products/page.tsx`) shows `ProductCard`s (same framed look as project cards). Each `/products/[slug]` page is static and works as an onboarding page: hero beside `components/ProductSignupForm.tsx`, cover, features, gallery, four setup steps, FAQ, CTA back to `#signup`, other products.
- The signup form posts to `app/actions/product.ts` (same honeypot, timing check and shared `lib/rate-limit.ts` limit as the enquiry form; business name required, phone optional). It saves a **product enquiry**: a normal `enquiries` row with `product` set to the slug (and `phone`), so the admin inbox can filter Projects/Products (`?type=`). Both emails name the product.

### Enquiries and admin

- `components/EnquiryForm.tsx` is a three-step form (topic → message → contact details), used on the homepage hero (`variant="compact"`, id `start`), the contact page and every service page (`defaultTopic` pre-selects the service and starts on step 2). Until it hydrates (or with no JS) all three steps render at once with native validation and post straight to the server action. After hydration it sets `is-enhanced`, shows one `<fieldset>` at a time with a progress bar, validates each step before moving on, moves focus to the new step, and shows a success panel. Values are controlled state, and submit calls the action inside `startTransition`, so React 19 never resets the fields. Server errors send the user back to the step with the first error.
- The form posts to the server action `app/actions/enquiry.ts` via `useActionState`. The action validates, drops a filled `website` honeypot, rate-limits 5/hour per IP **in memory** (nginx overwrites `X-Forwarded-For`), runs the spam checks in `lib/spam.ts`, and inserts into `enquiries`. IPs are never stored. After the response, `after()` emails the enquiry to `MAIL_TO` via `lib/mail.ts` (nodemailer, pinned, over Zoho Mail SMTP: `smtppro.zoho.com:465`, `SMTP_*`/`MAIL_*` env vars; Reply-To is the visitor, with a link to the admin entry). It then emails the visitor a branded confirmation with a copy of their enquiry (Reply-To is the team inbox; capped at 2 per address per 24h in memory, message preview cut at 1,000 characters, so the form can't be used to mail strangers). A mail failure is only logged, never shown to the visitor; with no `SMTP_HOST` set, no email is sent.
- `lib/db.ts` is a pooled `mysql2` connection (TLS always on; `DB_CA_CERT_PATH` adds certificate verification). `lib/data.ts` holds all SQL. Both import `server-only`.
- Admin (`/admin`) is a single shared password (`ADMIN_PASSWORD`). `lib/auth.ts` issues an HMAC-signed, expiring, httpOnly cookie (`ADMIN_SESSION_SECRET`) scoped to `/admin`. **Every admin page and server action calls `requireAdmin()` itself**; there is no proxy/middleware, so a new admin page or action must do the same. Admin actions live in `app/admin/actions.ts`; panel pages are in the `app/admin/(panel)` route group. Admin pages are `noindex` (metadata, `X-Robots-Tag` header, robots.txt).
- Portfolio items (`portfolio_items`) are managed in the admin. The homepage shows the first five (by `sort_order`: one wide featured card, then a 2×2 grid), `/work` shows all, and each service page shows its own; public reads go through `lib/portfolio.ts`, which falls back to an empty list if the database is down. Cards are framed (image inset, text below, not overlaid): `title` sits above the `summary` headline, and `client` (used as the sector) and the service are tags along the bottom with the arrow tile. `image_url` is either a site path into `public/` (rendered with `next/image`) or a full external URL (plain `<img>`). Pages that show projects call `connection()` so they render per request and show new items immediately.
- Project pages (`app/(site)/work/[slug]/page.tsx`): `PageHero` (size `l`), the cover, then an article beside a sticky sidebar. The sidebar holds `components/CaseNav.tsx` (reading-progress bar and an "On this page" list that highlights the section in view and scrolls with Lenis), the project facts and a "Visit the live site" button; below 960px it sits above the article without the list. They read the case-study columns on `portfolio_items`: `slug`, `intro`, `scope` (one item per line), `overview`, `challenge`, `solution`, `results` (paragraphs separated by blank lines), `gallery` (one `src | alt` per line: the first image is full width in the article, the next two share a row as a 4:5 and a 6:5 image), and an optional `quote`/`quote_name`/`quote_role`. All are edited in the admin; empty fields drop their section. Parsing helpers and the card link rule are in `lib/case-study.ts` (safe for client components). Gallery images for the showcase projects are real screenshots of each live site in device frames, in `public/assets/work/<slug>-1..3.jpg`. The seeded copy is written from what each live site shows and makes no claims about results; add real outcomes and client quotes only once the client agrees them. `db/schema.sql` only creates missing tables, so `scripts/migrate.mjs` adds newer columns itself: add new columns to both.

### "Am I a Muslim?" quiz (/oneness.html)

- `public/oneness.html` is a self-contained static page (its own inline CSS and JS, plain black and white, outside the site design and layout): a tap-only quiz with a golden-spiral animation that writes "one" in a single cursive stroke. Next.js serves it as-is at `/oneness.html`; it is not in the sitemap or navigation.
- It talks to `app/api/oneness/route.ts`: `GET ?action=stats` (live counters, hidden if this fails), `POST ?action=finish` (anonymous totals plus per-question failed/unsure counts, once per device) and `POST ?action=lead` (name and WhatsApp number or email of people who ask to be contacted; 5 per IP per hour via `lib/rate-limit.ts`). SQL is in `lib/data.ts`; tables `oneness_stats`, `oneness_reasons` and `oneness_leads` are in `db/schema.sql`. Leads have no admin view yet: read them from the database. The question ids in the route must match the `id`s in the page.

### Spam protection and security

- `lib/spam.ts` (used by both form actions): each form fetches a server-signed, single-use token when it loads (`app/actions/form-token.ts`, HMAC with `ADMIN_SESSION_SECRET`); a token less than 3s old, tampered with or reused marks the submission as spam. The token is kept in React state and rendered as a controlled hidden input (a hidden input whose value is set directly is reset by React on every re-render). A content score flags link stuffing, HTML/BBCode links, common spam pitches, throwaway email domains and random-letter names (spam at 3+, or 2+ without a valid token, so no-JS visitors still get through with a normal message). Repeats of the same email and message within a day are ignored; at most 3 accepted per address per day and 40 per hour site-wide. Spam and repeats get the normal success response and are only logged as "not saved: spam/duplicate"; all of this is in memory. When testing, use `@squaberry-test.invalid` addresses and delete the rows afterwards.
- `next.config.ts` sends a Content Security Policy (scripts, styles, fonts and requests only from this site; images also from https; no plugins, framing or off-site form posts), HSTS in production, `X-Frame-Options: DENY`, `Permissions-Policy`, COOP and `nosniff`, and limits server-action bodies to 100kb. Adding a third-party script, embed, font or API means updating the CSP (and the privacy policy).
- Nothing on the site accepts file uploads. Everything users type is escaped (React, and `escapeHtml` in `lib/mail.ts`); the only raw HTML is `components/JsonLd.tsx`, which escapes `<`. SQL always uses placeholders. Admin sign-in allows 5 failed attempts per IP per 15 minutes, adds a delay after each failure, and its cookie is `SameSite=Strict`.

### Media (DigitalOcean Spaces)

- All media in `public/assets` and the share cards in `public/og` are uploaded by `scripts/upload-media.mjs` to the `sbsi-cdn` Space under `squaberry/` (same paths), public-read with a one-year cache, and served from `NEXT_PUBLIC_MEDIA_URL` (the Spaces CDN; read at build time, so set it before `npm run build`). Each raster under `/assets` also gets resized WebP copies (`name.w640.webp` etc.) at the widths in `lib/media.mjs`, which `next.config.ts` uses as `deviceSizes`/`imageSizes`.
- `next/image` uses the custom loader `lib/image-loader.ts`, which maps an `/assets/...` src and width to the matching WebP copy on the CDN, so the server does no image work. Plain `<img>` tags use `mediaUrl()` from `lib/media-url.ts`. With `NEXT_PUBLIC_MEDIA_URL` empty everything falls back to the local files (unresized). Database `image_url`/`gallery` values stay as `/assets/...` paths.
- After adding or changing a file in `public/assets` or `public/og`, run `npm run media:upload` (skips unchanged files; `-- --force` re-uploads all). Because of the long cache, give a replaced image a new file name. The `SPACES_*` keys are only needed where the upload runs and live only in the env files.

### SEO

- Every public page builds its metadata with `pageMetadata()` from `lib/seo.ts` (title, description, canonical, Open Graph, Twitter card); keep titles about 60 characters and descriptions under 160 (`clip()` trims long ones). Share cards are pre-rendered 1200×630 JPEGs in `public/og/<key>.jpg` (`home`, `about`, `services`, `work`, `products`, `contact`, `service-<slug>`, `product-<slug>`, `work-<slug>`) in the site's own design; a project without a card falls back to its first gallery image. Re-render and upload a card when its page's headline changes, and add one for new projects.
- Structured data (`lib/schema.ts`, rendered by `components/JsonLd.tsx`): Organization and WebSite on every page (from the `(site)` layout), BreadcrumbList on subpages, Service, SoftwareApplication + FAQPage, and CreativeWork on service, product and project pages.
- Icons: `app/icon.svg` (gradient square with the white mark), `app/favicon.ico`, `app/apple-icon.png`, `public/icon-192.png`/`icon-512.png` (manifest, and the Organization logo) and `app/manifest.ts`. `app/sitemap.ts` lists every visible page and project; `app/robots.ts` blocks `/admin`.
- Speed: public portfolio reads are cached for 10 minutes (`unstable_cache`, tag `portfolio` in `lib/portfolio.ts`) and admin saves call `updateTag` so changes show at once. Step forms show only their opening step before hydration (`js-form` class set by the inline script in `app/layout.tsx`, with spacing that matches the hydrated form) so pages don't jump; if a form hasn't hydrated within 6s all steps show.

### Styles

- `app/globals.css` is the whole public design system: tokens on `:root` (`--bg`, `--surface`, `--fg`, `--lav`, `--grad`/`--grad-hover`/`--grad-text` and `--spark`, `--cream`, radii, `--gutter`, `--ease-soft`, font variables from `next/font`), soft-square buttons (`.btn` + `.btn-icon`, 14px radius: white by default with a gradient hover; `.is-accent` is the gradient button; `.is-dark`, `.is-ghost`, `.is-lg`), panels (`.panel-lav`, `.panel-cream`), the 12-column `.bento` with `.span-*` classes, cards, marquees, the step form, and motion. Motion: `.rise` is the hero load-in, `app/(site)/template.tsx` fades each page in (`.page-enter`) and the header dock slides in once. Scroll reveals (`.reveal`, `.tilt-in`, `.text-reveal`) work in every browser: an inline script in `app/layout.tsx` adds `js-reveal` to `<html>` before paint (skipped under reduced motion, removed after 3s if the observer never starts), which hides those elements, and `components/RevealObserver.tsx` adds `is-in` as they enter (staggering ones that arrive together) and `is-done` once finished so hover transitions take over. It also watches for new elements (route changes, filters). Use tokens, not raw colours.
- i3media.net is a reference for mood only (dark, soft, lavender). Don't copy its layouts, components or wording: the header, buttons, footer strip and project pages were deliberately reworked to differ from it.
- The admin matches the public site: `app/admin/admin-base.css` (shared controls: gradient soft-square `.button`, dark fields, `.mono` labels) and `app/admin/admin.css` (sidebar, top bar, inbox with status tabs and a Projects/Products filter, detail, portfolio, sign-in) build on the public tokens and fonts from `globals.css`, scoped to `.admin`/`.admin-login`. Admin-only tokens are prefixed `--a-`; never redefine public tokens there. Both are imported by the admin layouts. To check the admin locally without the real password, run a second dev server with a throwaway `ADMIN_PASSWORD`/`ADMIN_SESSION_SECRET` in its environment (process env overrides `.env.local`), and don't commit that config.

### Content constraints

The privacy policy (`app/(site)/privacy/page.tsx`, `#form` section) states exactly what the enquiry form collects, that enquiries are stored in a DigitalOcean database in Singapore and a copy is emailed to the team inbox on Zoho Mail and a confirmation to the visitor, and that IPs are only held in memory. It also says the site sets no tracking cookies (only the admin sign-in cookie). Fonts are self-hosted by `next/font`; the only third-party requests are images from DigitalOcean Spaces, which the `#visit` section mentions. Changing form fields, storage, rate limiting, or adding analytics/cookies/embeds requires updating it to match.

## Deployment

Ploi: a daemon runs `npm run start` on 127.0.0.1:3090 and nginx proxies to it. Full steps are in `deploy/ploi-deploy.md`; the nginx config is `deploy/nginx-ploi.conf`. After deploying, run `npm run db:migrate` and then `npm run db:portfolio` once so production has the showcase projects and their pages. Production's `.env` must set `NEXT_PUBLIC_MEDIA_URL` before the build, or images are served unresized from the server.
