## Commands

```bash
npm install
npm run dev          # http://127.0.0.1:3000 (loopback only)
npm run build        # production build; also type-checks
npm run start        # serve the build on 127.0.0.1:${PORT:-3090} (production, behind nginx)
npm run typecheck    # tsc --noEmit (delete .next first if it complains about moved pages)
npm run db:migrate   # apply db/schema.sql and add any newer columns (safe to re-run)
npm run db:portfolio # upsert the 10 showcase projects and their case-study copy (matched by site URL)
```

There is no test suite or linter. Verify by running the dev server and checking pages at desktop and narrow phone widths (CSS breakpoints are 1100px, 960px and 640px) for horizontal overflow, keyboard focus and reduced motion. The built-in browser pane only captures a corner of an emulated viewport; Playwright full-page screenshots (saved under the gitignored `.playwright-mcp/`) are more reliable. Scroll reveals keep below-the-fold content hidden until it is scrolled to, so before a capture run `document.querySelectorAll('.reveal,.tilt-in,.text-reveal').forEach(e=>e.classList.add('is-in','is-done'))` and inject `.rise,.page-enter,.dock{animation:none!important}`.

Configuration comes from `.env.local` (development) or `.env` (Ploi production); `.env.example` lists every variable. Both env files are gitignored and must never be committed. The local env points at the **real** DigitalOcean database, so anything you submit locally lands in production data: clean up test enquiries and portfolio items afterwards.

## Architecture

Next.js 16 App Router, TypeScript, React 19, MySQL via `mysql2`. No CSS framework; Lenis provides inertia scrolling and Lucide (`lucide-react`, pinned) provides every icon.

- **Pages:** public pages live in the `app/(site)` route group, whose layout adds `SmoothScroll`, `SiteHeader` and `SiteFooter`: home, `about`, `services` (overview) and `services/[slug]` (six service pages), `work` (all projects with service filters) and `work/[slug]` (one case-study page per project), `products` and `products/[slug]` (see Products below), `contact`, `terms` and `privacy` (both via `components/LegalPage.tsx`). `app/not-found.tsx` sits outside the group and renders the header and footer itself. Each page renders its own `<main id="main">`. Old `*.html` URLs redirect permanently in `next.config.ts`.
- **Service content** lives in `lib/services.ts`: names, slugs, copy, `topics` (the enquiry form's topic options and the server-side allowlist) and `serviceStyle` (icon and accent colour per service). A service with `hidden: true` keeps its content but is left out of `services` (so it isn’t shown, linked, offered as a form topic or listed in the sitemap), its page 404s, and `next.config.ts` redirects its URL to `/services`. Display numbers (01, 02…) follow the visible order. Currently hidden: cloud & infrastructure, AI & workflow automation, strategy & consulting. Service images are `public/assets/services/<slug>.png` and project covers are `public/assets/portfolio/<slug>.png` (both generated with Higgsfield). "How we work" steps are in `lib/process.ts`. The About page team ("Core team" and "Development team", three people each, rendered by `components/TeamGrid.tsx`) lives in `lib/team.ts`: names, roles and bios are placeholders to replace, and a member without `image` shows a placeholder portrait; real photos go in `public/assets/team/` (about 4:5) with their path set as `image`.
- **Shared chrome:** `components/SiteHeader.tsx` (client: a single floating "dock" bar with the logo, nav links beside it (current page marked by a small lime square via `aria-current`), the email address and a lime "Start a project" button; a Services panel that drops under the dock (Services is a button controlling `#services-menu`; it opens on hover, click or ArrowDown, closes on Escape, outside click, moving onto the dimmed page (`.nav-scrim`) or below 960px; its subtitles and "Popular" links are `featureCopy` and `offers` in the component, filtered to visible services); and below 960px a full-screen menu that stops Lenis, locks scrolling and closes on Escape) and `components/SiteFooter.tsx` (a strip of soft-square service tiles sliding in two rows, linking to the enquiry form, then link columns and the legal row). `components/SmoothScroll.tsx` starts Lenis (skipped under reduced motion), exposes it as `window.squaberryLenis`, and re-syncs it after every route change so Next.js's scroll-to-top sticks.
- **Building blocks:** `PageHero` (page opener for Projects, Services, each service page, About, Contact, Terms and Privacy: eyebrow and title on the left; lead, optional `aside` and `actions` on the right; only the 404 page keeps the centred `.page-hero`), `SectionIntro` (eyebrow label with a small lime square, then a large heading; no rule line; `tone="light"` on lavender/cream panels), `ProcessSteps` (the four "How we work" cards used on home, Services and About: gradient icon tile in the step's accent, outlined step number), `ProjectCard` (framed cover image, name, headline, tags along the bottom; `featured` puts the image beside the text; links to the project page, or the live site if a project has no slug), `ProjectsBrowser` (client filter chips + bento grid for `/work`), `Icon` (maps short names such as `web` or `arrow-up-right` to Lucide icons; add new icons to its map, never hand-drawn SVG paths; the admin uses `AdminIcon`, also Lucide) and `EnquiryForm`.

### Products

- `lib/products.ts` holds the four products (Gym Management System, Fast Food Management System, WhatsApp AI Assistant, AI Chatbot Integration): copy, features, gallery, FAQs, accent and icon, plus the shared `onboardingSteps` and `signupInterests`. The feature copy is a draft: the Fast Food system's comes from the Chips n Chops platform (`D:\Project\Github\ChipsnChops`: admin, API and mobile app); the others need confirming. Images are in `public/assets/products/` (Higgsfield); the gym and food galleries reuse the real site screenshots in `public/assets/work/`.
- `/products` (`app/(site)/products/page.tsx`) shows `ProductCard`s (same framed look as project cards). Each `/products/[slug]` page is static and works as an onboarding page: hero beside `components/ProductSignupForm.tsx`, cover, features, gallery, four setup steps, FAQ, CTA back to `#signup`, other products.
- The signup form posts to `app/actions/product.ts` (same honeypot, timing check and shared `lib/rate-limit.ts` limit as the enquiry form; business name required, phone optional). It saves a **product enquiry**: a normal `enquiries` row with `product` set to the slug (and `phone`), so the admin inbox can filter Projects/Products (`?type=`). Both emails name the product.

### Enquiries and admin

- `components/EnquiryForm.tsx` is a three-step form (topic → message → contact details), used on the homepage hero (`variant="compact"`, id `start`), the contact page and every service page (`defaultTopic` pre-selects the service and starts on step 2). Until it hydrates (or with no JS) all three steps render at once with native validation and post straight to the server action. After hydration it sets `is-enhanced`, shows one `<fieldset>` at a time with a progress bar, validates each step before moving on, moves focus to the new step, and shows a success panel. Values are controlled state, and submit calls the action inside `startTransition`, so React 19 never resets the fields. Server errors send the user back to the step with the first error.
- The form posts to the server action `app/actions/enquiry.ts` via `useActionState`. The action validates, drops spam quietly (`website` honeypot, or submitted < 3s after the `started` stamp), rate-limits 5/hour per IP **in memory** (nginx overwrites `X-Forwarded-For`), and inserts into `enquiries`. IPs are never stored. After the response, `after()` emails the enquiry to `MAIL_TO` via `lib/mail.ts` (nodemailer, pinned, over Zoho Mail SMTP: `smtppro.zoho.com:465`, `SMTP_*`/`MAIL_*` env vars; Reply-To is the visitor, with a link to the admin entry). It then emails the visitor a branded confirmation with a copy of their enquiry (Reply-To is the team inbox; capped at 2 per address per 24h in memory, message preview cut at 1,000 characters, so the form can't be used to mail strangers). A mail failure is only logged, never shown to the visitor; with no `SMTP_HOST` set, no email is sent.
- `lib/db.ts` is a pooled `mysql2` connection (TLS always on; `DB_CA_CERT_PATH` adds certificate verification). `lib/data.ts` holds all SQL. Both import `server-only`.
- Admin (`/admin`) is a single shared password (`ADMIN_PASSWORD`). `lib/auth.ts` issues an HMAC-signed, expiring, httpOnly cookie (`ADMIN_SESSION_SECRET`) scoped to `/admin`. **Every admin page and server action calls `requireAdmin()` itself**; there is no proxy/middleware, so a new admin page or action must do the same. Admin actions live in `app/admin/actions.ts`; panel pages are in the `app/admin/(panel)` route group. Admin pages are `noindex` (metadata, `X-Robots-Tag` header, robots.txt).
- Portfolio items (`portfolio_items`) are managed in the admin. The homepage shows the first five (by `sort_order`: one wide featured card, then a 2×2 grid), `/work` shows all, and each service page shows its own; public reads go through `lib/portfolio.ts`, which falls back to an empty list if the database is down. Cards are framed (image inset, text below, not overlaid): `title` sits above the `summary` headline, and `client` (used as the sector) and the service are tags along the bottom with the arrow tile. `image_url` is either a site path into `public/` (rendered with `next/image`) or a full external URL (plain `<img>`). Pages that show projects call `connection()` so they render per request and show new items immediately.
- Project pages (`app/(site)/work/[slug]/page.tsx`): `PageHero` (size `l`), the cover, then an article beside a sticky sidebar. The sidebar holds `components/CaseNav.tsx` (reading-progress bar and an "On this page" list that highlights the section in view and scrolls with Lenis), the project facts and a "Visit the live site" button; below 960px it sits above the article without the list. They read the case-study columns on `portfolio_items`: `slug`, `intro`, `scope` (one item per line), `overview`, `challenge`, `solution`, `results` (paragraphs separated by blank lines), `gallery` (one `src | alt` per line: the first image is full width in the article, the next two share a row as a 4:5 and a 6:5 image), and an optional `quote`/`quote_name`/`quote_role`. All are edited in the admin; empty fields drop their section. Parsing helpers and the card link rule are in `lib/case-study.ts` (safe for client components). Gallery images for the showcase projects are real screenshots of each live site in device frames, in `public/assets/work/<slug>-1..3.jpg`. The seeded copy is written from what each live site shows and makes no claims about results; add real outcomes and client quotes only once the client agrees them. `db/schema.sql` only creates missing tables, so `scripts/migrate.mjs` adds newer columns itself: add new columns to both.

### Styles

- `app/globals.css` is the whole public design system: tokens on `:root` (`--bg`, `--surface`, `--fg`, `--lav`, `--lime`, `--cream`, radii, `--gutter`, `--ease-soft`, font variables from `next/font`), soft-square buttons (`.btn` + `.btn-icon`, 14px radius; `.is-lime`, `.is-dark`, `.is-ghost`, `.is-lg`), panels (`.panel-lav`, `.panel-cream`), the 12-column `.bento` with `.span-*` classes, cards, marquees, the step form, and motion. Motion: `.rise` is the hero load-in, `app/(site)/template.tsx` fades each page in (`.page-enter`) and the header dock slides in once. Scroll reveals (`.reveal`, `.tilt-in`, `.text-reveal`) work in every browser: an inline script in `app/layout.tsx` adds `js-reveal` to `<html>` before paint (skipped under reduced motion, removed after 3s if the observer never starts), which hides those elements, and `components/RevealObserver.tsx` adds `is-in` as they enter (staggering ones that arrive together) and `is-done` once finished so hover transitions take over. It also watches for new elements (route changes, filters). Use tokens, not raw colours.
- i3media.net is a reference for mood only (dark, soft, lavender and lime). Don't copy its layouts, components or wording: the header, buttons, footer strip and project pages were deliberately reworked to differ from it.
- The admin matches the public site: `app/admin/admin-base.css` (shared controls: lime soft-square `.button`, dark fields, `.mono` labels) and `app/admin/admin.css` (sidebar, top bar, inbox with status tabs and a Projects/Products filter, detail, portfolio, sign-in) build on the public tokens and fonts from `globals.css`, scoped to `.admin`/`.admin-login`. Admin-only tokens are prefixed `--a-`; never redefine public tokens there. Both are imported by the admin layouts. To check the admin locally without the real password, run a second dev server with a throwaway `ADMIN_PASSWORD`/`ADMIN_SESSION_SECRET` in its environment (process env overrides `.env.local`), and don't commit that config.

### Content constraints

The privacy policy (`app/(site)/privacy/page.tsx`, `#form` section) states exactly what the enquiry form collects, that enquiries are stored in a DigitalOcean database in Singapore and a copy is emailed to the team inbox on Zoho Mail and a confirmation to the visitor, and that IPs are only held in memory. It also says the site sets no tracking cookies (only the admin sign-in cookie). Fonts are self-hosted by `next/font`, so no third-party requests are made. Changing form fields, storage, rate limiting, or adding analytics/cookies/embeds requires updating it to match.

## Deployment

Ploi: a daemon runs `npm run start` on 127.0.0.1:3090 and nginx proxies to it. Full steps are in `deploy/ploi-deploy.md`; the nginx config is `deploy/nginx-ploi.conf`. After deploying, run `npm run db:migrate` and then `npm run db:portfolio` once so production has the showcase projects and their pages.
